# ADR 0012 — Idempotency-Key required on every state-changing request

**Status:** Accepted · **Date:** July 2026 · **Stage:** 6 (§5)

## Context
The Concept Note requires draft-saving and retry sync for the two forms mentors complete on the ward floor.
That guarantees every mutating request in the mentor and student journeys is sent more than once, and that
some arrive hours late. Duplicate session logs nobody can explain are the predictable field failure.

## Decision
`Idempotency-Key` (a UUID) is **required** on every state-changing request, generated by the client at
form-open time and reused unchanged across retries. It is the primary key of `core_idempotency_key`, so a
replay is a primary-key conflict inside the same transaction as the business write.

## Consequences
- Replays return the original response with `Idempotency-Replayed: true`, and cannot double-apply.
- Idempotency cannot be half-committed: the key and the business row commit together or not at all.
- Key reuse with a different payload is a 409, surfaced as a client bug rather than silently resolved.
- Idempotency is checked *before* authorisation, so a replay still returns the original result after the
  actor's scope has changed.
- `GET /commands/{command_id}` lets a client reconcile a lost response without generating write traffic.

## Rejected
**Optional idempotency.** Optional means absent on the one path that matters.
**Server-side dedupe by payload hash.** Cannot distinguish a genuine second session on the same day from a
retry, which WFR-014's five-minute window exists to separate.
