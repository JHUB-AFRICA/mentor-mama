## 1. Request lifecycle

### 1.1 Goal

Turn `requested_facility` from a silent pointer into an auditable request the facility can **accept, decline (with reason) or partially accept**, that the coordinator can **withdraw or re-route**, and that **reminds and expires**.

### 1.2 Data model — decision: new tables, keep the pointer

Fields on `Placement` cannot hold history (a student can be declined by A then requested of B) or per-item decisions. Recommended:

```
RequestBatch                     (one coordinator submission to ONE facility)
  id, institution, facility, created_by, allocation_run (FK, nullable),
  window_start, window_end, note, expires_at, last_reminded_at,
  reminder_count, created_at
  status  (derived, not stored: open | decided | expired | withdrawn)

PlacementRequest                 (one placement inside a batch = one decision unit)
  id, batch (FK), placement (FK), facility (FK, denormalised),
  status: pending | accepted | declined | withdrawn | expired | superseded | fulfilled
  decline_reason: capacity | no_mentor | ward_closed | dates_unsuitable |
                  student_unsuitable | other        (controlled vocabulary, like PauseReason)
  decline_note (text, required when reason=other)
  decided_by (FK user, null), decided_at, version (int)
```

Rules enforced in the database (same style as `models.py` constraints):

- `UniqueConstraint(fields=[placement], condition=Q(status__in=[pending, accepted]), name="one_open_request_per_placement")`.
- `CheckConstraint`: `declined` ⇒ `decline_reason` not null; `decided_at` not null for every non-`pending` status.
- `Placement.requested_facility` stays as a **denormalised read pointer** maintained only by the request service (the incoming selector at `selectors.py:40` and the portal's `requested_facility_name` keep working). Migration backfills one batch + one `pending` request per placement that currently has `requested_facility_id` set and `facility_id` null.

Alternative rejected: add `request_status`/`decline_reason` columns to `Placement`. Cheaper, but loses re-request history and cannot express partial acceptance per batch.

### 1.3 States and transitions

```
                     (coordinator creates batch)
                                │
                                ▼
                          ┌──────────┐  withdraw (coordinator)   ┌───────────┐
                          │ PENDING  │──────────────────────────▶│ WITHDRAWN │
                          └──────────┘                           └───────────┘
                           │   │   │  expires_at passes (system)  ┌─────────┐
          accept (NM) ◀────┘   │   └─────────────────────────────▶│ EXPIRED │
          decline (NM) ◀───────┘                                   └─────────┘
              │         │
              ▼         ▼
        ┌──────────┐ ┌──────────┐   re-request to another facility
        │ ACCEPTED │ │ DECLINED │──────────────────────────────────┐
        └──────────┘ └──────────┘                                  ▼
          │      │                                     new PENDING request
          │      └─ withdraw (coordinator, only before ward allocated) ─▶ WITHDRAWN
          │ ward allocated by arrange / manual allocate_ward
          ▼
     ┌───────────┐
     │ FULFILLED │   (terminal; placement now has a facility derived from the ward, INV-17)
     └───────────┘
 Old request replaced by a new one while still PENDING/DECLINED/EXPIRED  →  SUPERSEDED
```

| From             | To                       | Actor / capability                       | Guard                                                  | Side effects                                                  |
| ---------------- | ------------------------ | ---------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------- |
| –                | pending                  | coordinator `request_facility`           | placement `draft`, `facility_id` null, no open request | pointer set, `PlacementsRequested` (batched)                  |
| pending          | accepted                 | NM `decide_placement_request`            | request facility = NM facility                         | optional soft capacity hold (see 1.5)                         |
| pending          | declined                 | NM                                       | reason required; `other` needs note                    | pointer cleared, coordinator notified (one summary per batch) |
| pending/accepted | withdrawn                | coordinator `withdraw_placement_request` | placement still `draft` with no ward                   | pointer cleared                                               |
| pending          | expired                  | system (beat task)                       | `expires_at < now`                                     | pointer cleared, both sides notified                          |
| declined/expired | superseded + new pending | coordinator                              | same as create                                         | history kept                                                  |
| accepted/pending | fulfilled                | system inside `allocate_ward`            | ward belongs to request facility                       | mark in same transaction as ward assignment                   |

**Partial accept** is not a separate state: the NM submits one decision call carrying `accept: [ids]`, `decline: [{id, reason, note}]`. The batch is "decided" when no item is pending. Arrange (existing one-click) still works on `pending` + `accepted`; items it places become `fulfilled`, items it cannot place stay as they are, so the NM must decline or leave them (reminders cover the latter). A student the facility does not place and does not decline is **not** auto-declined.

### 1.4 Idempotency and concurrency

| Operation                                      | Rule                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create batch / decide / withdraw               | Wrapped in `IdempotentCommand` (existing). **Change:** `result_ref` stores the `RequestBatch.id` (or `AllocationRun.id`), and replay returns the stored result payload instead of `{"replayed": true}` (fixes D5).                                                                                      |
| Locking                                        | Lock `Placement` rows `ORDER BY id` with `select_for_update()` inside the transaction before reading/writing requests, so two batches containing overlapping students cannot deadlock or both win. The current bulk `.update()` in `_record_requests` is replaced by per-row guarded writes (fixes D6). |
| Decision races                                 | Each `PlacementRequest` carries `version`; decide/withdraw does `UPDATE … WHERE id=… AND status='pending' AND version=:v`; zero rows ⇒ `409 RequestAlreadyDecided` returning the current state, never an overwrite.                                                                                     |
| NM vs coordinator race (accept while withdraw) | Whoever commits first wins; the loser gets 409 with current status; no state is partially written because both go through the placement row lock.                                                                                                                                                       |
| Expiry vs decision                             | Expiry task uses the same guarded update; a decision committed just before expiry stands.                                                                                                                                                                                                               |
| Retried beat task                              | Reminder/expiry tasks select by `last_reminded_at`/status and are safe to run twice.                                                                                                                                                                                                                    |

### 1.5 Does acceptance reserve capacity?

No hard hold in the first release (a hold would need releasing and complicates `facility_free_capacity`). Acceptance is a soft signal shown in the coordinator's split preview ("accepted but not yet arranged") and is subtracted from the _declared free capacity_ in `plan_facility_split` so the same free slot is not offered twice. Decision recorded in §8 (Q1).

### 1.6 UI needs

- Coordinator register (`CoordinatorPlacementRegister.tsx`, `CoordinatorPlacementDetail.tsx`): request status chip (Pending / Accepted / Declined: reason / Expired), "Re-request" and "Withdraw request" row actions, batch drawer showing per-student decision.
- Nurse manager (`NurseManagerDashboard.tsx` incoming card, `ArrangeStudentsModal.tsx`): add "Review request" step with per-student accept/decline checkboxes and reason select before Arrange; show expiry countdown.

## 2. Change governance after arrangement

### 2.1 Principle

Authority split from ADR 0028 is kept: **the facility owns ward and mentor; the institution owns facility and dates.** Anything that crosses the line needs the other side's approval. Programme Admin is the audited fallback. Every change needs a typed reason (min 10 characters server-side; the portal already forces one for bulk reassign) and an audit row.

### 2.2 Who may change what

`D` = direct (actor acts, reason required) · `P→X` = proposal that role X must approve · `—` = blocked (use withdraw + new placement)

| Change                      | draft / scheduled                                                                                                 | awaiting_student / orientation / induction                             | active / paused                                                                                                    | completed / archived / withdrawn |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------- |
| Mentor swap                 | NM `D`; **Coordinator `D` (override, §2.6)**                                                                      | NM `D`; Coordinator `D` (override)                                     | NM `D` (new mentor must be available; handover notice); Coordinator `D` (override, NM notified first-class)        | — (`_reject_closed` already)     |
| Ward (same facility)        | NM `D`; **Coordinator `D` (override)**                                                                            | NM `D`; Coordinator `D` (override) (student must re-acknowledge, §2.5) | NM `P→Coordinator`; Coordinator `D` (override); no approval wait needed because the coordinator is the approver    | —                                |
| Facility (different)        | Coordinator `D` before release (clears ward/mentor, re-opens request lifecycle); NM `P→Coordinator`               | Coordinator `D` with re-acknowledgement; NM `P→Coordinator`            | —                                                                                                                  | —                                |
| Dates (`planned_start/end`) | Coordinator `D`, NM notified; window re-checked against ward capacity (override flag if it breaks capacity, §2.6) | Coordinator `D`, NM notified (NM may object within 48 h, Q3)           | Extend only: Coordinator `D`; NM `P→Coordinator` (shortening blocked; pause already extends `actual_end`, POL-020) | —                                |
| Student replacement         | — (withdraw with `administrative_error` + new placement)                                                          | —                                                                      | —                                                                                                                  | —                                |

Today none of the ward/facility/date rows exist as commands except mentor swap; ward change is currently blocked by D2.

### 2.3 Model

```
PlacementChangeRequest
  id, placement (FK), kind: ward | mentor | facility | dates
  proposed_by (FK), proposed_at, reason (text, required)
  payload (JSON: {ward_id} | {mentor_id} | {facility_id, ward_id} | {planned_start, planned_end})
  base_version (int)          -- placement.version when proposed (optimistic lock)
  required_approver_role      -- computed from the matrix above, stored
  status: pending | approved | rejected | withdrawn | expired | applied | failed
  decided_by (FK), decided_at, decision_note
  applied_at, failure_reason
```

Constraint: one `pending` change request per `(placement, kind)`.

Direct changes (`D`) do **not** create a pending request; they run a command (`change_ward`, existing `reassign_mentor`, `change_dates`) and write an already-`applied` row so the history timeline is uniform.

### 2.4 Rules

- **Approval is applied in the same transaction as the decision**, under the placement lock, re-running every guard (capacity over the window, mentor policy, student overlap exclusion). If the guard now fails, status becomes `failed` with a domain error code and the proposer is told; nothing is half applied.
- `base_version` mismatch (placement changed since the proposal) ⇒ `409 PlacementChangedSinceProposal`; the approver sees the diff and must re-confirm.
- **Dates:** a date change must update `Placement.planned_*`, the open `StudentAssignment.started_on`, and respect the `student_no_overlapping_placements` exclusion; it must not move the window past recorded sessions or pauses (`verify_session_write` window).
- **Ward change:** closes the open `WardAssignment` (`ended_at`, `end_reason`) and creates a new one in one transaction under `facilities.lock_ward`; capacity counted over the placement window (fixes D2/D3). If the ward is in another facility, it is a _facility_ change.
- **Mentor swap:** keep `reassign_mentor` (sessions/induction stay on the placement, per its docstring); make `reason` mandatory at the serializer; recipients: new mentor, previous mentor, student (if released), coordinator (summary).
- **Blocked once closed:** `_reject_closed` / `_reject_terminal` stay the single gate for every new command. While `paused`, only mentor swap and dates-extend are allowed; ward/facility changes are blocked.
- **Audit:** `audit.record(... changes={"ward": {"from","to"}}, override_reason=reason)` exactly like `reassign_mentor`. Proposals and decisions each write an audit row.
- **Expiry:** pending change requests expire after 7 days (default, Q3); expiry notifies the proposer.

### 2.5 Student re-acknowledgement

Existing: `PlacementAcknowledgement` is a `OneToOneField` to the placement and `confirm_student_placement` rejects a second signature (`AcknowledgementAlreadySigned`). It records only name + time, not what was signed.

Proposed:

- Add `acknowledged_snapshot` (JSON: ward id/name, facility, mentor id, dates) to the acknowledgement at signing time (additive migration; backfill null).
- Define a **material change** = ward, facility or dates changed after the student signed (mentor swap is _not_ material by default, Q4).
- On a material change in `awaiting_student | orientation | induction`: set `Placement.reack_required_at`; do not change state; the Student sees "Details changed, please review"; induction **sign/activate (T-10) is blocked** until a new acknowledgement is stored (new `PlacementAcknowledgement` revision rows instead of OneToOne: change to FK + `revision`, latest wins).
- On a material change in `active | paused`: no state change, student is notified and sees the new details; re-acknowledgement is requested but does not block session logging (Q4 default).
- Student-facing UI is out of scope here; contract is `reack_required: bool` on the participant placement payload and `POST /placements/{id}/confirm` accepting a new revision.

### 2.6 Coordinator override (new)

Direction received: the coordinator can override an arrangement and make the changes needed. Today this is not possible: `allocate_ward`, `assign_mentor` and `reassign_mentor` require capabilities that exclude the coordinator (`identity/capabilities.py` — `allocate_ward`, `assign_mentor` are NM + PA only), and `require_scope` would let a coordinator through only on `institution_id`, which the services pass for the placement.

| Aspect                   | Rule                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capability               | New `override_arrangement`: Coordinator + PA. Narrow: it permits `change_ward`, `reassign_mentor`, and `change_dates` on placements **of the coordinator's own institution** and only while the placement is not closed. It does **not** grant `arrange_placements` (the one-tap auto-arrange stays facility-owned) or access to other institutions.                                |
| Targets                  | The coordinator picks a ward/mentor from a **partner facility's** active wards/accepting mentors (`facilities.scoped_wards`, `identity.active_mentors`) via a read endpoint that exposes only name, free capacity over the window and mentor load, never mentor contact details.                                                                                                    |
| Reason                   | Required, min 10 characters, stored as `override_reason` in the audit row exactly like `reassign_mentor`; free-text categories optional (Q15).                                                                                                                                                                                                                                      |
| Capacity                 | Default: **respects capacity** (`WardCapacityExceeded` still applies). Exceeding declared capacity requires `exceed_capacity=true`, a second typed confirmation, and a notification to the NM. This is only permitted once the programme answers whether declared capacity is binding (existing open question; memo row C-08 says hard block). Until answered the flag is rejected. |
| Facility authority       | The facility's nurse manager is notified immediately (in-app + email, matrix row 25) and sees an "Overrides" entry in the run history, with before/after. The NM can raise an objection note (no automatic revert).                                                                                                                                                                 |
| Interaction with runs    | An override on a placement created by an `AllocationRun` marks the `AllocationRunItem` as `overridden` (not `undone`), so undo (§3.3) skips it instead of reverting a human decision.                                                                                                                                                                                               |
| Release                  | Coordinator still releases manually (T-03). Overriding a released placement triggers the re-acknowledgement rules in §2.5.                                                                                                                                                                                                                                                          |
| Audit                    | `placement.override.ward`, `placement.override.mentor`, `placement.override.dates`, `placement.override.facility`, each with `changes` before/after and `override_reason`.                                                                                                                                                                                                          |
| Why direct, not proposal | The coordinator is the approver for facility/date changes in §2.2, so a proposal would approve itself. The control is the mandatory reason, audit and NM notification, not a wait.                                                                                                                                                                                                  |

ADR 0028 receives a short amendment recording this (done in the same change). The authority statement "a coordinator never allocates wards" becomes "a coordinator never allocates wards _through the automatic arrange_; an explicit, audited override is allowed".

## 3. Automatic allocation improvements

### 3.1 Rules (hard = never violated, soft = tie-breakers)

| Rule                                               | Type                          | Today                                                                                     | Change                                                                                                                  |
| -------------------------------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Ward free capacity over the student's own window   | Hard                          | In plan (`_ward_load`, pipeline states); admission check in `allocate_ward` has no window | One shared function `ward_free(ward, start, end)` used by both plan and `allocate_ward` (D3)                            |
| Ward not archived / not closed in window           | Hard                          | Archived filtered in `scoped_wards`                                                       | Add closures (§4)                                                                                                       |
| Mentor same facility, active, `accepting_students` | Hard                          | Yes (`active_mentors`, `mentor_assignment_policy`)                                        | Keep                                                                                                                    |
| Mentor under `max_active_placements`               | Hard                          | Yes, but counts finished placements (D1)                                                  | Count only non-closed states, and only placements **overlapping the window** (concurrent load)                          |
| Mentor required training complete                  | Soft (prefer) + release block | Preferred via `required_modules_complete`; release blocked when programme flag set        | Add programme flag `auto_arrange_requires_trained_mentor` (default **true** = hard) — Q6                                |
| Conflict of interest (mentor ↔ student)            | Hard                          | None                                                                                      | New `MentorConflict(mentor, student, reason, declared_by)`; excluded from candidates, reason never shown to the student |
| Mentor unavailable in window (leave, rotation)     | Hard                          | None                                                                                      | `MentorUnavailability` (§5)                                                                                             |
| Previous mentor of the same student                | Soft                          | None                                                                                      | Policy flag: `neutral` (default) / `prefer_same` / `avoid_same` — Q7                                                    |
| Even spread across mentors                         | Soft                          | `max(trained, remaining, -planned)`                                                       | Use `remaining ratio` (`remaining/limit`) so a limit-2 mentor is not drained before a limit-8 mentor                    |
| Order fairness                                     | Soft                          | Seeded random shuffle                                                                     | Keep default; optional `order=request_time` (Q8)                                                                        |

### 3.2 Preview parity

- `plan_*` returns `plan_hash = sha256(sorted candidate ids + ward loads + mentor remaining + strategy + seed)`.
- Apply request carries `expected_plan_hash`; mismatch ⇒ `409 PlanChanged` + a fresh preview payload so the NM re-confirms. Without the hash the old behaviour (re-plan with the seed) remains for API clients, but the portal always sends it.
- Apply executes **the reviewed assignments** (ward/mentor ids), re-validating each through `allocate_ward`/`assign_mentor` rather than re-deciding, so the only legal divergence is a per-row failure reported as `failed`.
- Property test: for random data, `apply(plan)` arranges exactly the plan rows minus rows that fail a hard rule at apply time (§7.4).

### 3.3 Run records, partial failure, undo

New `AllocationRunItem(run, placement, status: done | failed | skipped | undone, ward_before/after, mentor_before/after, error_code, error_message)`; `AllocationRun.status: running | completed | partial | failed | interrupted | undone | partially_undone`.

- Create the run row **first** in its own committed transaction (`running`), update items as each placement commits, then close with the summary. A beat task marks `running` runs older than 15 minutes as `interrupted` so a crashed worker is visible (fixes D4).
- Per-student transactions stay (already the design). Failed items are persisted with their domain error code; `POST /allocation-runs/{id}/retry-failed` re-plans only failed/skipped items with the same seed.
- Notifications are emitted once at the end from the persisted item list, so a partial run still sends accurate counts.

**Undo / rollback** (`POST /allocation-runs/{id}/undo`):

| Condition     | Rule                                                                                                                                                                                                                                                                                                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Window        | Within 24 h of run completion (setting `ALLOCATION_UNDO_WINDOW_HOURS`, default 24, Q9)                                                                                                                                                                                                                                                                                             |
| Per item      | Only if the placement is still in the state the run left it (`draft`/`scheduled`), the ward/mentor assignment is still the one the run created (`ended_at IS NULL`, same ids), and the placement has **not been released** (`awaiting_student` or later is never undone)                                                                                                           |
| Effect        | End the run's `WardAssignment` and `MentorAssignment` with `end_reason="allocation_undo"`; clear `facility_id`; return state to `draft` through a system-asserted T-04 (new `asserted_by="placements.allocation_undo"`; today T-04 is coordinator-only via the `create_placement` capability, so NM cannot use it); restore the request to `pending` (re-opens the incoming queue) |
| Partial       | Items that no longer qualify are reported `skipped` with the reason; run becomes `partially_undone`                                                                                                                                                                                                                                                                                |
| Who           | The actor who ran it, or a user with `rollback_allocation_run` in the same scope; Programme Admin always                                                                                                                                                                                                                                                                           |
| Notifications | Mentors/coordinators get one "arrangement withdrawn" summary; students unaffected because nothing was released                                                                                                                                                                                                                                                                     |

**Rebalance** is deliberately _not_ a separate engine: it is "undo selected items then re-run arrange with a new seed/strategy", with a preview. Mentor-only rebalance is in §5.

## 4. Ward management

### 4.1 Gaps

- Capacity is a single number per ward (`Ward.max_students`) edited only by Programme Admin (D9). There is no per-cohort/period capacity, no temporary closure, `shift_pattern` is free text (`CharField(120)`), and nothing warns when a facility is near or over what it declared.
- The coordinator split uses the same single number (`facility_free_capacity`).

### 4.2 Proposed model (additive)

```
WardCapacityWindow   ward, starts_on, ends_on, max_students, cohort (nullable),
                     declared_by, note            -- overrides Ward.max_students inside the window
WardClosure          ward, starts_on, ends_on (nullable = until reopened), reason (controlled), note,
                     closed_by, reopened_by, reopened_at
Ward.shift_pattern_code  enum: day | night | rotating | custom   (free text kept for custom)
```

Effective capacity over `[start, end]` = `0` if a closure overlaps; else the **minimum** capacity across overlapping windows (fallback `Ward.max_students`); `cohort`-scoped windows apply only to placements of that cohort. This single function is the one used by plan, `allocate_ward`, the coordinator split and the ward directory.

### 4.3 Rules

- Facility NM declares capacity windows and closures for **their** facility wards (new capability `manage_ward_capacity`: NM + PA). Programme Admin keeps base `max_students`/archiving (`update_programme_ward` unchanged). This resolves D9 without changing the "PA owns directory" decision.
- POL-007 stays: a window or closure cannot take effective capacity below the students already **occupying** it in that window (`WardCapacityBelowOccupancy`); students merely _scheduled_ in the window are returned as an impact list.
- **Closing a ward** with scheduled/awaiting placements in the window: the command returns `impacted_placements`; the NM must either confirm (placements move to a "needs ward" list and the NM is prompted to re-arrange; each is audited as a ward change with reason `ward_closed`) or cancel. Active/paused placements are never auto-moved; they are listed and require an explicit ward change (§2).
- **Capacity warnings** (computed, no storage): utilisation ≥ 80 % for any week in the next 90 days (amber), ≥ 100 % (red); incoming requested students > free capacity; declared windows ending soon.
- Shift patterns carry no allocation effect in this release (display and filter only).

### 4.4 UI (nurse manager)

Extend `NurseManagerPlacementWorkspace.tsx` ward tab (ward comparison table already exists per `.sinaps/state.md`): week-by-week occupancy bar per ward, "Declare capacity" and "Close ward" dialogs with impact list, warning chips, and a capacity banner inside `ArrangeStudentsModal.tsx` ("You are about to place 14 students; free capacity is 11").

### 6.3 Design decisions

- **Batching rule:** any command that touches more than one placement publishes one event per _recipient_, carrying counts and (for ≤ 5 items) placement ids; per-placement events are published only for single-item commands. Reuse `quiet_notifications()`; extend it so it suppresses `MentorReassigned`/ward-changed per-row events too (`_QUIET` is checked today only for `MentorAssigned` and `PlacementScheduled`).
- **Reminders:** a new Celery task `placements.tasks.send_request_reminders_task` runs hourly (`config/celery.py` beat), reads state from the DB (`last_reminded_at`, `reminder_count`) and publishes events; idempotent because a reminder is skipped if `last_reminded_at` is within the interval. Similar tasks: `expire_requests_task`, `expire_change_requests_task`, `ack_overdue_summary_task`, `mark_interrupted_runs_task`.
- **Copy:** replace the large `if/elif` plus inline dict in `email.deliver_outbox_event` for these events with a table `PLACEMENT_EMAIL_COPY[event_type] -> callable(payload, recipient) -> (subject, title, intro, detail)` in a new `notifications/placement_emails.py`, so counts/reasons can be rendered (D8) and `deliver_outbox_event` stays small. Plain-text output via `_email_content` stays (per `docs/engineering/email-design.md` the HTML redesign is separate).
- **Opt-outs:** extend the set in `_optional_email_enabled` (`email.py`) for new gated types; mark "not opt-out-able" ones by a `MANDATORY_EVENT_TYPES` set checked before preferences. No new preference column (reuses `placement_updates`); a separate "reminders" toggle is Q11.
- **Links:** deep links go to `/placements` today; add `?placement=<id>` / `?tab=incoming` once the portal reads it (portal task, §7.5).
